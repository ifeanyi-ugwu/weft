## What we protect

1. **Private keys.** Nobody, including web pages, the relay and Weft's own UI code, should be able to read them.
2. **Intent.** Nothing should be signed that the user didn't see and approve.
3. **Identity privacy.** Sites learn who you are only after you connect them.

## How

### Keys are non-extractable

Keys are generated by, or imported into, the browser's WebCrypto as **non-extractable** `CryptoKey` objects and stored in the extension's IndexedDB. Script can ask WebCrypto to sign with them but can never read the key material back, including Weft's own code. The background worker is the only place signing happens. ([ADR 0002](/reference/decisions/))

Fabric requires low-S DER signatures; Weft converts WebCrypto's output accordingly.

### Pages have no privileges

The provider in the page (`window.weft`) only posts messages. A separate content script forwards them to the background worker. The background worker takes the requesting site's origin from the browser, never from the message, so a page can't pretend to be another site.

### Every signature is checked

The relay builds the Fabric messages; Weft doesn't trust it to build the right ones. Before each signature, Weft decodes the protobuf bytes and checks:

- **Proposal:** channel, chaincode, function (with contract prefix), every argument, private-input names, endorsing organisations if requested, signer MSP ID and certificate, and that the transaction ID in the header matches.
- **Transaction:** same transaction ID and channel, and your certificate as creator.
- **Commit status request:** same transaction ID and channel.

Any mismatch stops the flow with "Weft refused to sign". This is covered by tests that build real messages with `@hyperledger/fabric-gateway` and tamper with them.

### Approval is explicit

Connecting a site doesn't authorise signing. Each evaluate and submit opens an approval window; closing it rejects. Reads and writes look different (teal and amber) so a write can't pass as a read.

### Hosts are granted one by one

The extension's manifest asks for no host access up front. When you add a network, the browser asks you to allow its CA and relay hosts.

## Not covered yet

- **Protection at rest.** v0 relies on your browser profile and OS account. Anyone who can use your unlocked browser profile can use Weft. The plan is to wrap keys with a passkey-derived key (WebAuthn PRF), so each session needs a passkey touch.
- **Lock timeout.** Related to the above: there's no "lock wallet" yet.
- **Revocation checks.** Weft doesn't check CRLs. The network rejects revoked certificates at endorsement.
- **Relay authentication.** Any wallet can ask a relay to build proposals; peers enforce who may actually transact. Restrict signers with `WEFT_ALLOWED_MSP_IDS`.

Please don't open a public issue. See `SECURITY.md` in the repository.
